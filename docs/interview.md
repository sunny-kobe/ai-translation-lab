# 面试表达与追问

以能亲自解释、复现和修改的部分为个人能力证据。当前有 AI 协作实现；没有完成的批量、并发调度和费用持久化不能包装成已经实现的亮点。

## 一分钟介绍

学习阶段可以这样介绍：

> 我做了一个独立的 AI 翻译学习项目，目标是理解从前端异步交互，到 HTTP 服务、数据库和模型调用的完整链路。它支持英文 key/value 输入、多语言任务、结果编辑与审核以及 JSON 导出。模型接入使用小型 provider 接口，当前真实模型是智谱 GLM-5.3-Flash。
>
> 我重点研究可靠性：任务先持久化再返回 202；worker 从数据库领取结果，校验模型输出，再按版本写回。人工编辑后的晚到模型结果会被丢弃，只有该语言全部成功且审核后才能导出。测试涵盖真实 PostgreSQL、部分失败和实际进程崩溃恢复。我也区分系统可靠性与翻译语义质量，后者仍需样例人工评审。

能独立复现上述机制后，再把“我重点研究”改成具体的设计、实现和取舍贡献；不要把代理生成代码当作已掌握的能力。

## 多 key × 多语言与并发

当前 `N` 个 key、`L` 种语言形成 `N × L` 条独立结果；最多 50 × 4 = 200。当前 provider 一次翻译一条，worker 串行调用，所以模型并发是 **1**。数据库 pool 的 `max=6` 与模型并发不是同一个参数。

优化方案是按同一 job、同一语言、模型/prompt 上下文分批；每批最多 10 keys，同时限制源文字符预算；初始模型请求并发 **2**。短样例、无失败的 50 × 4 可从 200 次请求降到 20 次，但输出更长、可能截断，返回集合也必须校验。并发 2 是待验证的初始值，不是宣称账户允许或全局最优。

方案已按 key-level provider、并发 2 和持久化调用记录实施；仍需区分已验证的机械可靠性与尚未完成的语义质量评审。

## 高频追问

**为什么不在 POST 中直接等待模型？**

模型耗时和失败不确定。先原子写入任务和结果，返回任务 ID，前端轮询；HTTP 服务接收任务与 worker 执行任务分开。202 表示已接受，不表示翻译已完成。

**为什么不用 Redis/BullMQ？**

当前本地单用户、一个 worker，PostgreSQL 同时保存队列状态和结果，先用较少组件验证正确性。需要多节点 lease、优先级、复杂延迟调度和更大吞吐时才评估队列组件。不能说 PostgreSQL 在所有规模下都优于 Redis。

**advisory lock 和 revision 分别解决什么？**

session advisory lock 保证同库同 schema 只有一个 worker 所有者；job/result 行锁保证数据库修改顺序；revision 是乐观并发条件，防止晚到结果和过期人工编辑覆盖较新内容。锁不是模型供应商计费幂等。

**重启恢复会不会重复调用模型？**

会。进程可能在模型已成功、数据库尚未提交时死亡；恢复后再次调用。因此不能声称 exactly-once。数据库唯一约束和条件写回保护结果完整性，但不保证供应商只计费一次。

**只加 Promise.all 就能提升并发吗？**

不能。当前运行中恢复逻辑会把所有 running 当作中断任务；直接并行可能重复领取仍在执行的结果。需要有界调度、明确在途归属、逐项事务写回、全局限流冷却和崩溃恢复。等待模型时也不能持有长事务。

**为什么并发不是越大越好？**

账户/模型并发限额、请求频率、输入输出 token、服务负载和本地数据库资源都构成约束。增加并发可能增加 429 与重复计费，收益反而下降。用成功吞吐、p95 时延、限流率和每条成功结果成本测量，再从 1、2、4 逐级选择。

**质量验证能证明翻译准确吗？**

不能。当前机械校验能发现结构、占位符、语言标识、术语或截断问题；错译但结构正确仍可能通过。语义评审需要独立样例、人工检查和失败记录；不能把 4/4 机械通过写成 100% 翻译准确率。

**安全边界是什么？**

模型密钥只存在本地后端 `.env`，浏览器不持有；只访问项目专属本地数据库；接口与模型结果都做运行时检查。这是回环地址的单用户学习应用，还没有生产身份认证、租户隔离或公网部署验收。

## 这次批量升级后的准确表述

> 我把调度单位从 `key × language` 改成 `key`。一个 key 请求携带最多 50 个目标语言，模型返回带语言代码的数组；系统再把它拆成逐语言结果保存、校验、审核和导出。这样 50 keys × 50 languages 的成功路径是 50 次模型请求和 2500 条结果，而不是 2500 次请求。worker 默认允许 2 个 key 请求同时在途，可配置 1–4。
>
> 我没有把批量 JSON 当作可信结果。返回 key、语言集合、重复语言、缺语言、占位符和术语都会检查；某个语言失败时只重试这个 key 中失败的语言，但下一次模型请求仍会带上这个 key 的待重试语言集合。每次请求有模型/prompt/usage/耗时记录，结果通过 revision 条件写回，人工修改不会被晚到结果覆盖。

面试时要明确：当前证据证明的是机械可靠性、请求数和并发上限；50 种语言的自然度和语义准确率没有被 4/4 或 2500 条结构通过替代。
